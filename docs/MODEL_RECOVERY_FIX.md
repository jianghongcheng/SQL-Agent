# 核对器误拒与模型暂态故障修复

## 原因与修复边界

修复前，用真实 qwen3:8b 重放 `orders:contract_alias`：主模型 SQL 和结果正确，但核对器直接返回 STOP，最终 `semantic_check_unavailable`。它没有执行另一条 SQL，所以不是行序/重复行比较器导致的误拒。仅在核对器提示中明确“输出别名不是源字段，不要求源表存在该别名”，原始复现便通过。此规则对任意明确 SQL AS 别名适用，没有写入该题答案或为特定表绕过检查；不能保证消除所有模型误拒。

暂态故障的最小测试在两种规划器上分别注入一次 TimeoutError、HTTP 429 和残缺 JSON，修复前 6 项全失败。原实现一次模型异常即结束规划或核对。现在两种规划器共用 `model_recovery.complete_json`，在相同输入上进行有限重试，随后原有响应 schema 验证、SQL 授权和结果核对继续执行。

## 明确的预算和停止条件

- 每次主规划/独立核对最多 **3 次模型调用尝试**，即初次加至多两次重试；SQL 修复仍最多 3 轮，独立核对仍只有一项独立查询计划。最坏情况为 9 次主模型请求加 3 次核对请求，不是无限重试。
- 仅重试超时/连接错误、HTTP 429/502/503/504 和 JSON 解析失败。有效 JSON 中的非法 action/schema、SQL 权限错误、结果不一致、明确 STOP 不由此机制重试。
- 默认退避 0.25 秒、0.5 秒。若 Retry-After 是 0–2 秒的数字则尊重等待值；过长、日期形式或无法解析时停止并交接，不提前撞限流。2 秒是本地恢复等待预算，不是行业标准；不支持长等待任务调度。
- 单次请求仍采用各 provider 配置的 timeout。默认 30 秒并非整个任务的截止时间；不能把此机制宣称为全任务 deadline、真实网络故障恢复 SLO 或完整资源隔离。
- 各任务保存 primary/checker 的失败类型、尝试数、等待和最终结果。明确 STOP 保持停止，永久故障或重试耗尽仍 `needs_review`。已知一般 SQL 输出即使核对一致仍不自动发布。
- 同一串行 worker 的每个任务结束后释放模型恢复日志，结果中保留该任务副本；不宣称一个 JobPipeline 实例支持并发调用。

## 验证方式

`tests/test_model_recovery.py` 覆盖首次失败后恢复、持续失败三次停止、明确 STOP 不重试、永久 HTTP 错误不重试、Retry-After 处理、非法响应 schema 不重试，以及实际 JobPipeline 的重试耗尽/不发布/连续任务日志隔离。

完整实验重跑 `scripts/validate_agent_reliability.py` 的原 108 次协议：相同题目、相同场景、相同三次完整试验、同一模型，评分代码不变。运行器唯一行为外的变动是把包装主规划器的恢复日志暴露给 pipeline，确保保存观测证据。旧 `agent_reliability_v1` 不覆盖。

这套实验的故障为注入异常/残缺响应；下一次真实模型调用正常响应才算恢复。没有模拟真实网络等待，不能以此推导实际宕机时间下的延迟。新增退避与调用耗时均计入 pipeline 延迟。

## 同协议复测结果

`outputs/validation/agent_reliability_v2/` 保留 108 份 episode、原始模型调用、源码/模型 manifest、日志和 `coverage_comparison.json`。核实模型 digest、题目/场景/重复次数与评分代码均与 v1 相同；没有遗漏或重复，运行期间源码不变。

|---|---:|---:|
| 正常可回答任务：正确且被控制器保留 | 42/45 | 45/45 |
| 可回答任务三次完整运行全部成功 | 14/15 题 | 15/15 题 |
| 正常应拒绝任务 | 18/18 | 18/18 |
| 同义改写任务 | 9/9 | 9/9 |

| 业务数据库被修改 | 0/108 | 0/108 |
| 自动发布 | 0/108 | 0/108 |
| 实际模型请求 | 162 | 198 |

108/108 达到本套已知合成任务的预设控制器结果，**不代表生产准确率、真实用户交付或任何隐藏外部基准成绩**。本轮没有观察到这些任务上的新错误保留；仅凭小型回归套件不能推断一般误放行率为零。

恢复额外消耗了 36 次真实模型调用（+22.2%），另有 27 次注入响应/异常，因此 v2 模型接口尝试共 225 次。正常可回答任务 pipeline P95 为 1,194.58 ms（v1 为 1,319.65 ms）；不同运行的计时波动不能解释成性能优化收益。没有 HTTP、队列、人工审核和真实故障等待时间，也没有货币成本。

最终全量回归 **113 passed**。持续失败、永久错误和明确 STOP 的停止行为由自动测试覆盖，不能混入“一次注入后正常”的 27 个恢复案例，宣称持续宕机也能完成任务。通用查询的自动发布策略未放宽，重试与核对一致仍不构成语义证明。

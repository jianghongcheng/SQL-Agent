# Agent 输出与上线验收：论文和 GitHub 证据

核查日期：2026-09-06。本文是资料核查和本项目验收方案建议，不是新实验结果，也不是上线认证。本轮没有修改运行策略、安装外部评测框架或执行外部基准。

## 结论和适用范围

要区分三个问题：一次输出是否满足任务要求；Agent 在任务分布、重复运行和故障条件下是否可靠；某个具体部署是否达到业务验收目标。一个输出不能证明后两者。

下列资料支持多维度评测、可执行任务验收、重复试验与线上监测。它们没有为本项目提供可以直接套用的统一生产合格分数。把多个分数加权成一个总分，也不能自动获得上线结论。

## 本项目建议采用的验收结构

以下是结合资料提出的项目方案，不是任何单篇论文规定的通用标准，尚未实施或验收。

### 每个任务的可执行验收

每条任务应预先声明：初始数据库状态、业务问题、时间与单位、允许的数据范围、必要输出、业务定义、禁止副作用，以及在信息不足时允许的处理方式。参考定义由数据或业务负责人确认，不能在看到模型答案后改成有利于模型的定义。

建议为每次完整运行分别记录：

| 维度 | SQL Agent 的具体检查 | 评分方法 |
|---|---|---|
| 任务完成 | 所有子问题都回答；字段、过滤条件、聚合粒度、金额口径符合定义 | 隐藏的程序断言、业务认可参考计算；分别记录部分完成与完整完成 |
| 数据证据 | 返回值可追溯到实际 SQL、数据库版本/快照、时间范围及工具响应 | 数值与执行产物逐项核对；不能仅以“生成了 SQL”算有依据 |
| 输出可消费性 | schema、类型、单位、空值、重复行、约定排序符合任务；不依靠未要求的字符串格式 | 结构断言；排序只在任务要求时约束。当前核对器的严格行序比较可能误拒，应单独审计 |
| 副作用和授权 | 只读任务未修改业务库；未读越权表或租户数据，未向外部发送结果 | 数据前后状态差异、访问记录、工具参数及网络行为；只读 authorizer 不等于完整数据授权 |
| 交互与停止 | 需要澄清时能识别缺失信息；工具失败不编造结果；停止或交接有可用证据 | 预设可回答、歧义和不支持任务；正确回答率与不必要拒答率分开统计 |
| 时延和资源 | 用户收到可用结果或有效交接所需总时延、总调用数、SQL 扫描资源、算力/API 成本 | 从提交到任务终态计时；故障、重试、核对及失败消耗均计入 |

对“按地区计算一月份扣退款后的收入”这一任务，不能只检查 SQL 返回了几行数字。验收还要明确订单日期还是退款日期、退款是否一对多、是否保留无订单地区、币种和时区，并用重复退款、空地区、月界时间等数据检查定义。上述例子是本项目测试设计建议，不是从论文直接复制的任务。

只读任务的业务数据库应保持不变，但服务写入审计/任务库是允许副作用；不能粗暴要求整个系统完全没有写入。轨迹检查应针对权限、预算、确认等必要约束，而非要求模型走唯一推理或工具路径。

### 多次运行与任务分布层面的验收

| 维度 | 建议指标和分母 | 需要保留的边界 |
|---|---|---|
| 重复可靠性 | 每题重置环境后进行多次完整试验，报告 pass^k 与每题成功分布 | pass^k 是 k 次全成功；pass@k 是 k 次至少一次成功；任务内部重试不是新的完整试验 |
| 扰动稳健性 | 同义改写、无关上下文、等价数据变换下的任务结果和成功率变化 | 必须先验证扰动确实保持含义；变了业务含义不能要求输出不变 |
| 故障恢复 | 对超时、限流、部分响应、schema 变化等，报告成功恢复、正确停止、错误继续的比例及额外成本 | 当前的少量故障注入不是完整压力测试，更不是实测故障发生率 |
| 对抗安全 | 正常效用、受攻击任务效用、攻击目标达成率分别统计 | 全部拒答不能被算作“安全且有用”；样本中未观察到违规不等于风险为零 |
| 选择性回答 | 错误自动发布率、回答覆盖率、不必要拒绝率、交接率与交接完成情况 | 自动发布为零时，其条件正确率没有定义；不能记为 100%。人工兜底时间和工作量必须计入 |
| 泛化与统计 | 按 schema、业务类型和难度分层；保留未用于调试的任务；报告重复次数和不确定性 | 当前 500 题已经用于分析，后续不能再称为未见测试集。相关任务/同题重复不能都当独立样本 |
| 成本收益 | 相同部署条件下，与直接 NL→SQL、普通重试、当前核对方案比较 | 可用结果的成本应包含失败和审核开销；固定业务查询也可作为该类任务的独立基线，不冒充通用问答基线 |

### 评判器也必须经过验收

建议先建立人工确认的正确、错误、应澄清和无法判定案例，测量 grader 的误放行与误拒绝；隐藏验收数据与模型运行时可见证据分开。对业务歧义、基准错误、基础设施失败和 Agent 错误分别记录，不把所有异常都归咎于模型。

业务参考 SQL 在同一数据库上与候选相等，是一个有限条件下的检查。独立模型生成两个相同结果，也不是语义证明。测试套件和人工校准能补证据，但不应被描述为绝对正确性的保证。

建议上线前以独立任务验收和压力测试作为证据；如有实际部署，再通过影子运行、受限试点、人工抽检、线上分布漂移监测及可回退机制观察真实结果。此部署流程是本项目建议，不能从离线实验直接推导“线上已可靠”。

## 对现有结果的重新定位

| 已有结果 | 支持的结论 | 不支持的结论 |
|---|---|---|
| BIRD Mini-Dev 500 题 | 固定模型和自定义限制下的参考执行结果一致性 | 实际业务任务分布上的上线通过率 |
| 核对后错误候选 217→72，正确候选 140→94 | 这一批冻结候选的筛查取舍 | 总体答题能力提高或自动放行已经足够安全 |
| 6/6 语义故障恢复 | 三个小型合成领域上的指定故障恢复链路有效 | 自然错误都能修复、复杂业务稳定成功 |
| 89 项软件测试 | 被覆盖的软件行为通过相应回归测试 | 重复模型稳定性、真实负载或整体安全风险达标 |
| 已有小规模 HTTP/worker 实验 | 对指定负载、恢复场景的局部证据 | 生产 SLO、长期可靠性或多租户隔离达标 |

现有指标无需丢弃，但缺少真实业务口径、独立任务验收、重复稳定性、成体系的扰动/攻击/故障评测、grader 人工校准及完整成本收益比较。它们是明确的证据缺口，不应被“生产级”一词遮盖。

## 适合接入的代码与优先顺序

1. **保留当前服务，先明确任务验收数据模型。** 用 `initial_state / task / allowed_actions / expected_outcome / graders / budget / trace` 表达一条任务；这是建议的数据结构，不是已存在的 API。
2. **优先研究 BIRD-Interact 的 Mini-Interact。** SQLite、SELECT-only 与本项目范围接近。先核实数据、参考测试可获得性和环境路径，再决定能否运行；没有执行，不承诺开箱即用。不得把完整 CRUD 基准分数与 SELECT 子集混报。
3. **借鉴 test-suite-sql-eval 的多实例语义测试。** 针对自己的业务 schema 生成测试数据并人工确认口径；不能直接把 Spider 的测试库接到 BIRD 当成同一个基准。
4. **从 τ 系列借鉴 end-state + 多次 trial，从 AgentDojo 借鉴 utility/security 双轨。** 都需要为 SQL 工具和数据权限编写任务适配，不需要把现有服务替换为客服或邮件 Agent。
5. **需要统一运行器时再接 Inspect AI。** 复用多 scorer、重复运行、统计和日志能力。框架选型不会替代业务 grader，也不因使用某框架获得认证。

本轮不填入 95%、99% 等合格线。下一份可验收协议应为每个目标写明：指标定义、任务范围、样本设计、错误代价、阈值来源、统计口径和不达标处理。来源可以是明确业务要求或被证实的成本/风险约束；若只是工程暂定值，就必须标注为暂定。

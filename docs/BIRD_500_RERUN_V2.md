# 修复后 BIRD Mini-Dev 全量复跑

本轮重新生成全部 500 道题，再对本轮新候选进行独立核对。不是复用旧预测，也不是 108 次合成任务测试的扩写。

## 协议与比较边界

沿用原 500 题、11 个 canonical 数据库、题目顺序、qwen3:8b 模型 digest、官方提供 evidence 和 CSV 字段描述、只读/函数/VM/结果行数限制以及原评分函数。`BenchmarkPlanner` 接入此次生产使用的有限模型恢复 helper；提示内容未改变。每题最多三轮 SQL 规划，单次模型请求最多三次传输/JSON 重试。

BIRD 没有应用方指定的输出契约，继续使用动态输出列适配，不能从 gold SQL 提取列名塞给模型。因此这次的输出别名提示修复并不适用于此 benchmark 核对分支。参考 SQL 只在 Agent 执行后进入离线评分器。

第一阶段是生产 bounded loop/只读执行器加 BIRD 输入适配；第二阶段是对新候选的一次独立核对计划（允许模型调用层恢复）。不是 HTTP/worker 端到端实验，也不是核对分歧后再做语义修复的实验。直接比较两个阶段时应保留此设计边界。

新增 6 次模型调用来自 1078、944、1481 三道题：每题的非合法 JSON 从一次尝试扩为三次，但重复错误仍未恢复。传输调用本身未记录异常；JSON 解析错误需从响应中识别，不能把 `calls_with_error=0` 误解为没有恢复尝试。三道题均保持停止。

生成阶段记录输入 token 1,963,139、输出 token 44,565；所有 604 次调用均有 usage。货币成本未估算。它说明提高暂态故障容错不自动提高通用 SQL 语义能力，而且确定性地重复同一错误会增加开销。

## 对本轮新候选的核对结果

| 指标 | 旧核对 v1 | 本轮核对 v2 |
|---|---:|---:|
| 覆盖的题目记录 | 500 | 500 |
| 实际核对模型调用 | 358 | 358 |
| 核对一致候选 | 167 | 172 |
| 一致且参考正确 | 94 | 96 |
| 一致但参考错误 | 72 | 75 |
| 一致但参考无法评分 | 1 | 1 |
| 不一致 | 129 | 132 |
| 核对不可用 | 62 | 54 |
| 主规划停止 | 142 | 142 |
| 已评分一致候选的条件正确率 | 56.63% | 56.14% |
| 初始正确候选保留率 | 94/140 | 96/140 |

本轮筛掉 142/217 个错误候选，同时损失 44/140 个正确候选。最终正确候选覆盖为 96/500=19.2%，不是 56.14% 的全题成功率。自动发布仍为零，这些只是离线核对保留的候选。

逐项审计显示：两次生成的全部 500 道题最终输出相同；全部 358 个核对输入提示字节相同；但有 17 个题目的 agreement 判定变化。此次核对没有模型调用异常，没有触发增加调用的 JSON 重试。故不能把 94→96 归因于修复；同样，72→75 提醒我们小幅数量变化不构成可靠性改善证据。固定 temperature=0、模型 digest 与输入也不能据本次观察假定推理输出必然完全可重复；本轮没有进一步定位波动的底层原因。

核对阶段输入 token 1,044,842、输出 token 25,048。两阶段共 **962 次真实模型调用**。核对时检查了主候选输出哈希；所有 500 个主记录在核对前后文件哈希一致；两阶段运行期间源码哈希均不变。BIRD 适配与模型恢复相关自动测试 26 项通过。

**结论：这次全量重跑没有证明通用 SQL 语义正确性提高。** 修复后的有限重试可以处理先前注入的一次性故障，但三道稳定非法 JSON 本次仍失败；合成别名案例的修复也不能泛化成所有 BIRD 场景的误拒已解决。下一步若要提高通用表现，需要针对语义失败与重复运行波动设计新的改动和独立验证，而不是把已有 108/108 合成结果当作答案。

# SQL 对照实验：432 次完整运行

日期：2026-09-06。执行前固定了[协议](PAIRED_SQL_BENCHMARK_PROTOCOL.md)、代码快照、模型 digest、数据与运行顺序；全部 432 条记录完成，源码与数据库哈希检查通过，结束时模型 digest 与开始时一致。

**结论：独立核对减少了错误候选保留，但没有提高正确候选数量；普通执行重试也没有改善这组语义错误。** 不能据此宣称 Agent 比一次生成答得更准。

## 数据与比较条件

库存、工单、物流三个 schema，12 类问题，各两份数据实例，共 24 个问题/数据组合。每个组合对比一次生成、最多三轮执行重试、最多三轮加独立核对器；正常与受控故障条件各完整运行三次。

432 是 episode 数，不是 432 道独立题。这是本轮新冻结的合成评估集，不是公共排行榜或真实企业工作负载；看过本轮结果后，它就成为开发/回归数据，不能继续称为未见留出集。

三种方法使用相同模型、问题、schema、输出契约和 SQL 安全边界，共享最多九次模型调用尝试的上限。一次生成仍使用共同的暂态故障重试 helper，但只做一轮 SQL 规划。实际调用量不相等，必须一起报告。

标准答案由独立 Python 集合、整数和日期计算在运行后评分。没有参考 SQL、答案行或 catalog fallback 进入主模型或核对器。所有通用输出仍需审核；下表“保留”指控制器 KEEP，不是自动交付给用户。

## 正常条件：每种方法 72 个 episode

| 方法 | 正确候选保留 | 错误候选保留 | 停止/交接 | 模型调用尝试 | 样本 pipeline p95 |
|---|---:|---:|---:|---:|---:|
| 一次生成 | 39/72 | 33 | 0 | 72 | 966.1 ms |
| 普通执行重试 | 39/72 | 33 | 0 | 72 | 948.1 ms |
| 独立核对 Agent | 30/72 | 0 | 42 | 192 | 3299.3 ms |

普通重试没有触发有效语义修复：SQL 能执行、字段检查通过，并不代表业务含义正确。核对器降低了错误保留，但也挡住了正确答案。正常组的正确保留率差异为 -12.5 个百分点；按 12 类问题聚类 bootstrap 的描述性区间为 [-33.3, 0.0]，不能将这个小型合成样本推广到全部 SQL 工作负载。

## 暂态故障条件：每种方法 72 个 episode

| 方法 | 正确候选保留 | 错误候选保留 | 停止/交接 | 含注入失败的调用尝试 |
|---|---:|---:|---:|---:|
| 一次生成 | 39/72 | 33 | 0 | 144 |
| 普通执行重试 | 39/72 | 33 | 0 | 144 |
| 独立核对 Agent | 30/72 | 3 | 39 | 261 |

每次故障 episode 在第一次主模型调用注入一次超时或 HTTP 429，之后调用真实 Ollama。注入没有模拟完整超时等待或持久故障。结果支持共同的传输重试 helper 恢复调用，不证明恢复后答案必然正确，也不能把这一共同机制算作独立核对器的收益。

核对器在 `open_by_team` 的三个 episode 中接受了错误答案，详见 `episode_0049.json`、`episode_0105.json`、`episode_0155.json`。模型一致不是正确性证明。这三个候选没有被服务自动发布。

## 重复可靠性、跨数据检查与成本

- 每题/实例/条件三次全成功的观察比例：一次生成与普通重试均为 54.2%，核对器为 41.7%；正常与故障组在此指标上相同。三次完整试验不同于一次任务里三次修复，不假定重复试验独立同分布。
- 把冻结的同一条候选 SQL 放到两份数据上执行：一次生成有 6 个 episode 在当前实例上正确，但换实例后未通过；这说明单实例结果相等可能只是偶合。
- 合并正常与故障条件，核对器挡住了 18 个正确候选 episode，没有观察到“首次错误经过修复后正确保留”的 episode。
- 合计 885 次尝试，其中 216 次为受控故障注入、669 次实际 provider 请求。记录了 401,365 个输入 token、42,093 个输出 token；216 次注入失败没有 usage，明确计为缺失，未估算美元成本。
- 所有业务源数据保持不变，所有 episode 在九次尝试上限内。所有方法自动发布数均为零，这是现有审核策略，不能拿来宣称零错误的生产系统。
- p95 只测 pipeline，不包括队列、HTTP 和离线评分；不是并发压测或生产 SLO。

# 通用 SQL 准确率提升：论文与实现核对

调研日期：2026-09-06。通过 academic-research MCP 检索论文、GitHub MCP 读取实现，并阅读下列固定版本论文的方法和实验。本文是接入建议，没有新增推理实验，没有修改生成器，也没有已验证的本地准确率收益。

## 本地证据与问题定位

[432 次对照运行](PAIRED_SQL_BENCHMARK_RESULTS.md)来自 12 类问题、24 个问题/数据实例组合，不是 432 道独立题。正常条件一次生成与执行重试均保留 39/72 个正确候选，核对器为 30/72。合并两种条件，核对器挡住 18 个正确候选；没有观察到首次错误经修复后正确保留。

因此，新增机制应针对能执行的语义错误：父子表连接导致重复统计、条件计数漏掉零值组、否定条件与 NULL、日期边界。仅提高可执行率不足以证明改善。小型合成 schema 只有少量表，不能把失败全部归因于 schema 检索；BIRD 的大 schema 与字段值匹配应另外分层评估。

## 论文证据

### CHASE-SQL：分解生成与候选选择

[论文 v1，§3.3–3.5、表 7](https://arxiv.org/html/2410.01943v1)：使用子问题分解、查询计划推理和在线合成示例构造不同候选；使用训练过的两两选择器。BIRD dev 消融：完整方法 73.01%，一致性投票 68.84%，一次提示排序器 65.51%；去掉分解生成器为 71.77%。这是该论文模型与候选预算下的结果，各模块增益不能相加，也不能推算 qwen3:8b 的提升。论文还报告未微调 Gemini 选择器的二分类准确率只有 58.01%。

适用推断：先生成简短、可审查的关系计划，明确每行代表什么、统计什么实体、连接基数、过滤位置、零值保留，再生成 SQL。先研究候选池是否包含正确答案，再研究选择器；同模型一致不是真值。此次没有核实完整官方 CHASE 训练代码与选择器权重，因此不把它列为可直接复现的安装包。

### CHESS：字段值检索与自然语言测试

[论文 v3，§3、表 4](https://arxiv.org/html/2405.16755v3)：在其抽样开发集配置中，完整工具为 64.62%，去掉实体/上下文检索为 59.86%，去掉修订为 57.82%。这是特定配置的模块消融，不能把修订收益解释成任意重试都有收益。论文也说明小 schema 下删减 schema 可能损害召回。

读取 [官方仓库](https://github.com/ShayanTalaei/CHESS)，固定到 Git tree `3d6e835f858d26885d21d4bc0215aeecf855efbe`：

- `src/workflow/agents/information_retriever/tool_kit/retrieve_entity.py`：LSH 找值，再做字符相似度和 embedding 过滤；实际使用外部 embedding 服务，不能直接宣称完全本地。
- `src/workflow/agents/unit_tester/tool_kit/evaluate.py`：LLM 对自然语言测试打分，汇总后选候选，平分时参考最大结果簇。这不是独立可执行 oracle，也不是正确性证明。
- `templates/template_generate_candidate_two.txt`：包含查询计划示例，但也包含优先 INNER JOIN、处理 NULL 等过度通用化规则，不适合直接拷贝到零计数任务。

建议借鉴值检索、列说明和候选差异检查。小 schema 保留完整关系；检索缩减主要用于大型 schema，并保留外键连接路径。

### ReFoRCE：用探查结果补充证据

[论文 v3，§3.2](https://arxiv.org/html/2502.00675v3)：列探索、答案格式约束和中间 CTE 执行反馈，面向 Spider 2.0 的复杂 schema/方言。适合借鉴逐步观察数据库的机制；其整体成绩不能视为单个探索模块的收益。

读取 [官方仓库](https://github.com/Snowflake-Labs/ReFoRCE)，Git tree `fd80efad09589f8074df7f8cb52dd10b9c740d45`，`methods/ReFoRCE/agent.py`：`exploration()` 生成探查 SQL，执行后把查询和结果带入上下文；该实现甚至会因探查 SQL 少于 10 条而重试。`self_correct()` 有空结果时简化条件的提示。这两项不能直接照搬：我们的预算有限，空结果也可能正确。

建议实现少量、有预算的只读探查：枚举条件值、查看 NULL/唯一性、检查关联重复。结果可以纠正数据理解，但不能凭数据猜测用户业务定义。CTE 中间执行需要先核对本地安全策略支持范围，不能为了兼容直接放宽写权限。

### OmniSQL：专用小模型基线

[论文 v2，表 3](https://arxiv.org/html/2503.02240v2)：同一 7B 基模型 Qwen2.5-Coder 的 BIRD dev 为 50.9%，经 SynSQL-2.5M 与增强 Spider/BIRD 训练的 OmniSQL-7B 为 63.9%；这是训练方案的比较，不是与本项目 qwen3:8b 的比较。训练使用 Spider/BIRD 训练集，不能称为完全未见这些基准分布。

读取 [官方仓库](https://github.com/RUCKBReasoning/OmniSQL)，Git tree `a66d732010c89fac4353488d1c59e0b06f92b742`，`train_and_evaluate/infer.py`：使用 vLLM、模型 chat template、SQL 代码块解析，输出上限 2048 token；脚本默认 n=4、temperature=1，不能用默认命令冒充论文 greedy 单次结果。

建议直接评估公开权重，不从头训练。先核对显存、权重格式和许可证，再建立单次 greedy 基线。当前项目强制 JSON 且输出 256 token，不能原样套用到输出推理与 SQL 代码块的专用模型；适配协议和长度限制必须记录，量化也是单独变量。

## 接入优先顺序与通用性

1. 固定 qwen3:8b，单独对比直接生成和“关系计划 → SQL”。计划字段覆盖输出粒度、实体键、关联关系、聚合、否定、NULL、日期区间，不按题号、表名或 benchmark 答案路由。先检查输出是否截断；提高 token 上限属于独立实验因素。
2. 增加 OmniSQL-7B 单次基线，区分模型能力变化与 Agent 编排收益。不能同时换模型、加工具、改预算后把收益全归功于 Agent。
3. 对需要数据证据的问题加入有界探查；小 schema 不强制裁剪。字段名/真实值检索主要针对 BIRD 类失败，关系计划主要针对当前聚合和反连接失败。
4. 最后试少量不同生成策略的候选与选择。先记录候选池中“至少一个正确”的离线上限；如果池里没有正确答案，增加核对器解决不了生成问题。

例如“没有 work 事件的工单”需要的是排除存在 work 事件的工单，同时保留无事件和只有 note 的工单。关系计划应明确这种存在性语义，而不是把所有否定问题硬套成同一条 SQL 模板。可在离线数据副本中加一条 note 检查结果是否应保持不变；这属于我们提出的性质测试，性质必须由需求确定，不能称为论文已证明有效的自动真值判定。

## 判断提升的实验约束

- 已看过的 500 题与本次合成题只作开发/回归。最终增益必须在事先冻结、未用于修改的新问题和新 schema 上确认，按聚合、反连接、值匹配等类型分层。
- 比较原始生成正确率、最终正确保留率、错误保留率、正确候选误拒率；不把拒绝更多题当作准确率提升。
- 同时报告调用、token、延迟和每条轨迹；调用上限相同并不等于实际成本相同，另做预算匹配对照。
- 对多候选报告池内正确答案覆盖率及选择成功率。gold SQL/期望行只进离线评分，不能进入探查、生成或在线选择器。
- 保留重复运行和多数据实例执行检查；单次结果相等可能偶合。空结果、重复行与排序语义按题目要求判断。
- 本轮为文献与实现调研。以上方法均未在本项目验证增益，不据论文分数宣称生产级准确率。
